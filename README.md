# 二连杆机械臂：从运动学推导到强化学习控制

一个纯 numpy + PyTorch 的二连杆机械臂仿真平台，不依赖 ROS、不依赖 GPU、不需要真实硬件。
包含完整运动学（正解 / 逆解 / 雅可比 / 奇异分析）、三个经典控制器基线，
以及一个只看得到 `(观测, 奖励)`、从零试错学出来的 PPO 策略。

## 效果

在 50 个随机初始姿态 + 随机目标上评测（seed=500）：

| 控制器 | 成功率 | 平均步数 | 它知道什么 |
|---|---|---|---|
| 完全不动 | 0% | 200.0 | 什么都不知道 |
| 随机推 | 8% | 189.2 | 什么都不知道 |
| PPO 冷启动 + `dist` 奖励 | **10%** | 181.0 | 只知道观测和奖励 |
| **PPO 冷启动 + `progress` 奖励** | **86%** | **52.0** | 只知道观测和奖励（只改了奖励写法） |
| BC 模仿（看伺服演示） | 76% | 99.0 | 看过 2.3 万条专家动作 |
| BC + PPO 微调（dist 奖励） | 78% | 59.5 | 演示 + 自己再试错 |
| **BC + PPO 微调（progress 奖励，400 轮）** | **90%** | **42.1** | 同上，只是奖励换写法、训练够长 |
| 雅可比伺服（gain=1.5，默认） | 94% | 53.4 | 知道杆长、知道雅可比 |
| **雅可比伺服（gain 调到 1.0）** | **98%** | 67.2 | 同上，只是参数调对了 |

三句话说清这张表：

1. **同一个 PPO、同一套超参、同一个环境，只把奖励从 `-0.5d` 改成 `10·(d_prev − d)`，
   成功率从 10% 跳到 86%。** 这一条推翻了我自己前一版的结论，详见《实验六》。
2. **纯 RL 第一次超过了模仿学习**：不看任何演示的冷启动就有 86%，
   而"BC 预热 + 400 轮微调"达到 **90%**，平均只要 **42.1 步** —— 比伺服的 67.2 步还快 37%。
   RL 在这里学到的不只是"够得着"，还有"怎么够得更省"。
3. **伺服仍然是最高的 98%**，而且它靠的是已知方程，不是试错。
   这条没变，也不该变：能写出公式的时候就用公式。

> BC 的两个数字差（76%/99.0 步 vs 早期记录的 78%/65.2 步）不是矛盾，
> 是**演示专家不同**：早期拿 `gain=4.0`（84%）演示，现在拿 `gain=1.0`（98%）演示。
> 演示质量改变的是步数（65→99），成功率几乎不动 —— 这本身也值得记一笔。

## 基准修正：我把 84% 当了一整晚的"专家"

写前几节的时候，我一直拿 `make_resolved_rate(gain=4.0)` 当专家基准，它测出来是 84%。
直到做延迟实验时发现一件怪事：**给动作加延迟，伺服反而变好了**（84% → 100%）。

延迟不应该让控制器变好，除非它本来就在震荡。扫一遍增益就明白了：

| gain | 成功率 | 平均步数 |
|---|---|---|
| 0.3 | 27.5% | 189.6 |
| 1.0 | **98.0%** | 67.2 |
| 1.5 | 94.0% | 53.4 |
| 2.0 | 94.0% | 44.0 |
| 4.0 | 84.0% | 49.1 |
| 8.0 | 82.5% | 47.4 |

**`gain=4.0` 太大了，控制器一直在过冲、在目标附近来回抖。**
延迟因为起了低通滤波的作用，恰好压住了震荡，所以"加了延迟反而更好"。

这件事的教训不是"要调参"，而是更硬的一条：

> **一个没校准的基准，会让所有对比结论都失真。**
> 我拿 84% 当"专家上限"，于是得出"BC 只差 6 个点、已经几乎追平"；
> 真实数字是差 20 个点，模仿学习的损失远比我说的大。
> 差 6 个点和差 20 个点，是"这个方法基本可用"和"这个方法还差得远"两种完全不同的结论。

所以本仓库里所有标着"专家"的数字，都以 `gain=1.0`（98%）为准；
`gain=1.5`（94%）是默认值，因为它在成功率和步数之间更均衡。

**`sweep.py` 把两个变量一起扫，还挖出一个更有意思的组合：**

```
最优点：gain=3.0 + delay=3  ->  100% / 34.6 步
```

高增益本来会震荡（92.5% → 87.5% → 82.5% 一路掉），配上延迟反而回到 100%，
而且比 gain=1.0 快一倍。**延迟在这里不是噪声，是"提前量"**——
控制器按 3 步之前的状态算，相当于一个粗糙的预测补偿。

这也是单变量思维最坑的地方：只扫延迟会以为"延迟有用"，只扫增益会以为"高增益有害"，
**放在一起才看见它们是一对互补的参数**。

## 为什么做这个

`ik_analytic()` 需要杆长、需要知道结构是二连杆、需要能推出闭式解。
真实机器人有六七个关节、有冗余、有摩擦和负载，**没有闭式解，模型也不准**。
PPO 不知道任何一条运动学公式，它只是反复试、看奖励、改策略。

这个项目就是把这个对比放在同一张桌子上，而不是停留在口号上。

## 技术要点

**1. 正运动学就是矩阵连乘**

`T = R(θ1)·Trans(L1,0) · R(θ2)·Trans(L2,0)`，每个关节一个齐次矩阵。
自检里用矩阵连乘的结果和三角公式对照，误差 `0.000e+00`。
关节数增加时，矩阵法只需继续往右乘，不用重新推导公式。

**2. 逆运动学的两组解来自 `sin θ2` 的 ±**

```
cos θ2 = (r² − L1² − L2²) / (2·L1·L2)
sin θ2 = ±√(1 − cos²θ2)      ← 这个 ± 就是"肘朝上 / 肘朝下"
```
`r > L1+L2` 或 `r < |L1−L2|` 时无解 —— 不可达是数学结论，不是程序判断。

**3. `det J = L1·L2·sin θ2`，为 0 即奇异**

奇异点不是"够不到"，而是"某些方向动不了，或要无穷大的关节速度才能动"。
实测：末端沿径向往外走 1 m/s 时——

| θ2 | 纯伪逆要求 | DLS(λ=0.05) 要求 |
|---|---|---|
| 0.5° | **282.15 rad/s** | 1.41 rad/s |
| 2° | 70.54 | 5.25 |
| 10° | 14.12 | 9.42 |
| 90° | 1.72 | 1.71 |
| 179.5° | **118.02** | 3.29 |

这就是工业控制器必须带阻尼的原因：不是优化选项，是电机烧不烧的分界线。
注意 DLS 不是免费的——它在奇异处的速度反而**变低**，意味着**放弃了那一段的精确跟随**，用精度换稳定。

**4. 环境的 `terminated` 与 `truncated` 必须分开**

`terminated`（够到了）之后未来价值确实归零；
`truncated`（超时）只是被掐断，它明明还能继续走。
把两者当一回事，等于告诉 agent「够到和超时一样糟」，训练必然崩。
这个坑在 CartPole 上也踩过一次，代价是几轮白跑。

**5. PPO 的连续动作处理**

高斯策略、`tanh` 把均值压进 `[-1,1]`、GAE 算优势、`clip(ratio, 1±0.2)` 限制单步更新幅度。
裁剪的作用不是"更快"，是"不许把已经学到的策略一步推翻"。

## 调试记录：五个 bug，和一次真正的失败

冷启动 PPO 跑了两版都是 2%，中间挖出五个 bug。前三个修完仍不收敛，
第四、五个修完之后才走到 78%。**这五个都是"程序不报错、曲线看起来很平静"的那种 bug**，
比语法错误难得多，也是这个仓库里最值钱的部分。

**① `log_std` 没有上界** —— 被梯度一路推大，采样几乎全落到 `[-1,1]` 之外、被 clamp 成 ±1，
策略退化成"bang-bang 乱撞"，熵跑到负值。

**② `log_prob` 用了裁剪前的动作** —— 环境执行的是裁剪后的动作，importance ratio 和真实动作对不上。

**③ 收敛阈值 0.02 m 太严** —— 随机策略几乎不可能命中，整个 buffer 里成功样本接近 0，
`+10` 那个终止奖励从来没被真正利用过。放宽到 0.05 m 后仍是 2%，说明它不是主因。

**④ `clamp` 把 `log_std` 锁死（这一条最隐蔽）** —— 我用
`log_std.clamp(log(0.1), log(0.6))` 限制标准差，而 **clamp 在边界外的梯度恒为 0**。
BC 阶段负对数似然天然偏爱小方差，把 `log_std` 一路推到下界以下；
之后 PPO 微调时梯度再也流不回来，熵**恒定在 -1.767 一动不动**——
策略永久退化成确定性，没有探索，微调把 BC 的 80% 拖到 66%。
改成软映射 `0.1 + 0.5·sigmoid(log_std)` 后，熵才恢复流动（0.74~0.85）。

**⑤ `critic` 从随机初始化直接进 PPO** —— BC 只用负对数似然训了 actor，
value 网络还是随机权重。于是前几十轮 critic 严重估错，advantage 全是噪声，
梯度把已经学好的策略往沟里带（第二版就是这么掉到 58% 的）。
补上策略评估（用 BC 策略采样、把 critic 回归到真实折扣回报）之后，
微调不再破坏起点。

**当时的判断（修完五个 bug 仍然失败）：**
这个任务要求 agent 从零学出"关节角 → 末端方向"的映射，也就是在网络里重新发明 `J⁺`；
而成功样本极稀疏，稠密奖励 `-d` 只能说"现在多远"，说不出"这一步走对没有"。
**当时我下的结论是：冷启动 PPO 不是调参问题，是任务性质不匹配。**

> **这个结论后来被实验六推翻了。**
> 上面最后一句话里其实已经写了病因 ——"说不出这一步走对没有"——
> 这是**奖励函数**的问题，不是任务本身的问题。
> 我只是把因果归到了"任务太难"，而没有去改那一句话指出的东西。
> 换成 `progress` 奖励后，同一个网络、同样从零开始，冷启动直接到 86%。

## 实验三：加限位，然后假设被推翻了

**原假设**：给 θ₂ 加关节限位（20°~160°），伺服会被墙挡住，专家失效，RL 就有机会超过它。

**实际结果**：

| | 无限位 | 有限位 |
|---|---|---|
| 专家（伺服） | 84.0% / 49.1 步 | **100.0% / 24.9 步** |
| BC | 78.0% / 65.2 步 | 80.0% / 60.2 步 |
| BC + PPO 微调 | 78.0% / 59.5 步 | **94.0% / 30.2 步** |

> 注：本节数字是当时用 `gain=4.0` 测的（见《基准修正》）。换成调优后的 `gain=1.5`
> 复测，无限位 94%、有限位同样不低于它 —— "限位不让专家失效"这个结论不变。

**专家不但没失效，反而从 84% 涨到 100%，步数减半。**

原因就一句话：`det J = L1·L2·sin θ2`，而 θ₂ = 0° 和 180° **恰好就是奇异点**。
把这两端屏蔽掉，雅可比永远不退化，任务是变健康了，不是变难了。
这个结论我在上文《技术要点 3》里刚写过，动手设计实验的时候却忘了 ——
**知道一个公式，和能用它预测实验结果，中间隔着一整个工程。**

**但这次翻车换来一个更硬的收获：**

把两个任务放在一起看同一套微调流程——

| 任务 | 微调带来的提升 |
|---|---|
| 无限位（含奇异区） | 78% → 78%（**+0 个点**），只有步数快了 8.7% |
| 有限位（无奇异区） | 80% → 94%（**+14 个点**），步数也从 60.2 降到 30.2 |

同环境、同超参、同起点，唯一区别是**训练样本里有没有病态的奇异区**。

这几乎坐实了一件事：**冷启动 PPO 失败的另一个原因是奇异区**。
那里末端动一点点、关节要甩几十度，梯度信号极端且剧烈，策略根本学不出来 ——
不是"探索不够"，是**那片区域的动力学本身对梯度下降不友好**。

所以对"RL 什么时候有用"这个问题，答案要再收紧一层：

> RL 在**动力学良好、但没有解析模型**的问题上发力。
> 动力学本身病态的地方（奇异、接触、碰撞），它和传统方法一样吃力。

## 实验四：关节摩擦死区 —— 这次专家真的失效了

前两次（限位、延迟）都是"扰动被副作用意外补偿"，所以失败。这次换一个补不回来的：
**关节静摩擦死区**。

```
|命令| < d      -> 关节一步都不动（推力顶不过静摩擦）
|命令| >= d     -> 实际速度 = sign(a)·(|a|−d)/(1−d)，满速时仍是满速
```

这不是震荡、不是超调，是**结构性推不动**：雅可比伺服在误差小时算出的关节速度本来就小，
正好整段落进死区，于是它会在离目标几厘米的地方永远停住。gain 调大只能把命令推过阈值，
但误差趋零时命令还是趋零 —— 精度和推力在死区面前是互相排斥的。

实验按 Sim2Real 的标准形态搭：**在理想模型（无死区）里采演示训 BC，再扔进真机（d=0.25）**。

| 控制器（真机环境，50 回合） | 成功率 | 平均步数 | 最终残距 |
|---|---|---|---|
| 伺服（**仿真里**的成绩单） | 98.0% | 67.2 | 8.5 cm |
| 伺服（真机，`gain` 从 0.5 扫到 128 取最好，g=32） | **80.0%** | 50.7 | 21.2 cm |
| 伺服 + dither（σ=0.3 抖动） | **95.3%** | 36.8 | 6.7 cm |
| BC（仿真训好直接上真机） | **0.0%** | 200.0 | 66.1 cm |
| BC + dither | 79.3% | 127.8 | 7.4 cm |
| BC + 真机 PPO 微调 · **确定性**部署 | **0.0%** | 200.0 | 42.7 cm |
| BC + 真机 PPO 微调 · **采样**部署 | **91.3%** | 84.0 | 5.4 cm |

**四条结论，一条比一条重。**

**① 死区确实让解析控制器结构性失效。** 伺服 98% → 80%，而且这 80% 是把 gain 扫了 9 个值、
挑出最好那个之后的成绩。BC 更惨：仿真里 76%，上真机 0%，**Sim2Real gap 76 个点**。
死区诊断直接对上了——BC 平均命令幅度 0.250，死区阈值正好 0.25，**每两步就有一整步完全推不动**。

**② 解药是"抖"，不是"更准"。** 给伺服加 σ=0.3 的随机抖动（dither），80% → 95.3%，步数还少了一半。
这是控制工程里突破静摩擦的老办法，本质是"用噪声把小信号抬过阈值"。

**③ RL 自己发现了要抖，但没赢过人工 dither。** 91.3% vs 95.3%，输了 4 个点，步数还多一倍（84 vs 37）。
诚实的结论是：**在"知道要抖、也知道抖多大"的前提下，人手设计的 dither 更划算；
RL 的价值在于它不需要人先想到这一点**——它只看到奖励，从 0% 自己爬到了 91%。

**④ 最有价值的一条：部署协议比算法更能决定成败。**

同一个网络、同一套权重：

| 部署方式 | 成功率 |
|---|---|
| 取均值（确定性，工程上最常规） | **0.0%** |
| 按分布采样（带随机性） | **91.3%** |

**差 91 个点。** 原因写在诊断里：确定性部署的平均命令幅度 0.237（< 死区 0.25，永远推不动），
采样时 0.384（噪声把它时不时抬过阈值）。

这件事我第一版就踩了：只报贪心评测，看到 0%，差点写下"RL 在这题上失败了"。
而训练日志里采样成功率明明是 85~100% ——**两个数都是真的，报哪个决定了结论正负**。

> 所以任何"RL 成功率"都必须注明部署方式。
> 不写部署协议的对比，等于不写单位的物理量。

## 实验六：只换奖励函数，冷启动 PPO 从 10% 到 86%

这篇 README 前面所有关于"冷启动为什么失败"的分析，都建立在一个前提上：
这个任务的奖励是给定的。可它明明是**我自己写的**。

原来的奖励：

```
dist 模式：r = -0.5·d - 0.01        "你现在离目标有多远"
```

问题是，这个数**几乎没有区分度**。实测连续 6 步：

```
dist     -0.9021  -0.9134  -0.9219  -0.9278  -0.9310  -0.9315
progress -0.2881  -0.2346  -0.1808  -0.1270  -0.0738  -0.0217
```

`dist` 走了 6 步，奖励只变了 0.03 —— 它回答的是"状态好坏"，
不是"我这个动作做对了没有"。而 advantage 是"这个动作比平均水平好多少"，
**当所有动作的奖励都差不多时，advantage 就是噪声**。
PPO 拿到的是"成没成功"这一个稀疏事件，前面几十步全是无效梯度。

换成 `progress`：

```
progress 模式：r = 10·(d_prev - d) - 0.01     "这一步走对没有"
```

它恰好是 potential-based shaping 的标准形式（Φ(s) = −d(s)，F = γΦ(s′) − Φ(s)），
Ng 1999 证明过**这种塑形不改变最优策略**，只把信号摊到每一步。
所以这是个极干净的对照：环境、动力学、最优解都没变，只改学习信号的密度。

**结果（同一环境、同一超参、同一 seed，唯一变量是奖励）：**

| 配置 | 成功率 | 平均步数 |
|---|---|---|
| PPO 冷启动 + `dist` 奖励 | **10.0%** | 181.0 |
| **PPO 冷启动 + `progress` 奖励** | **86.0%** | **52.0** |
| BC 基线（看 2.3 万条专家演示） | 76.0% | 99.0 |
| BC + `dist` 微调（旧流水线） | 78.0% | 59.5 |
| BC + `progress` 微调 | 50.0% | 121.8 |
| 伺服（上限） | 98.0% | 67.2 |

**三条结论。**

**① 冷启动失败，主因是奖励函数，不是任务性质。**
我上一版把病因归成"要从零发明 J⁺、任务性质不匹配"。真正的病根就写在同一段的最后一句里——
"说不出这一步走对没有"。我当时把这句话当成对**任务**的抱怨，
其实它是对**我自己写的奖励**的精确诊断。改完奖励，一样从零开始、一样不看演示，直接 86%。

**② 纯 RL 第一次超过模仿学习。**
86% vs BC 的 76%，而且它没见过任何一条专家轨迹。
这意味着 `bc_ppo.py` 那条"先克隆、再微调"的流水线，在这个任务上**本来就不必要**。
（流水线本身没错，它确实是真机上的标准做法；错的是把它当成"必须"。）

**③ 一个反常，和它的完整验证（`task_anomaly.py`）。**

BC + progress 微调只跑到 **50%**，比 BC 基线还低 26 个点。我给的假设是：
BC 学到的是伺服的"平滑风格"，`progress` 奖励的最优解却是"每步把 d 压到最低"的激进风格，
PPO 的 `clip=0.2` 限制单步更新幅度，150 轮不够走完这次切换，策略卡在两种风格之间。

假设必须能被证伪才有价值，所以设计了两个直接放开约束的对照组：

| 配置 | 成功率 | 平均步数 | 平均命令幅度 |
|---|---|---|---|
| BC 起点（平滑风格） | 76.0% | 99.0 | **0.134** |
| 原配置 `clip=0.2` / 150 轮 | 50.0% | 121.8 | — |
| C 放宽 `clip=0.4` / 150 轮 | 56.0% | 107.0 | **0.199** |
| **B 加长 `clip=0.2` / 400 轮** | **90.0%** | **42.1** | **0.375** |

**假设成立，而且比预想的更清楚。** 命令幅度 0.134 → 0.199 → 0.375 单调爬升，
说明策略确实在一路从"平滑"走向"激进"；而成功率是 **76% → 56% → 90%** 的 U 型：

> **中间态比两头都差。微调必须先变差，才能变好。**

这解释了一切：150 轮时它正卡在谷底，所以比不微调还糟糕；
放到 400 轮走完全程，反而拿到 **90%，超过从零训练的 86%，也超过所有其他 RL 配置**，
而且是全项目平均步数最短的（42.1 步，伺服要 67.2 步）。

**这条对工程的直接含义：微调中途停下来是危险的。**
不能因为"微调了反而更差"就判定 RL 没用 —— 那可能只是停在了 U 型的谷底。
判断要不要继续，得看风格的迁移方向（命令幅度这类可观测指标），不能只看成功率的当下值。

顺带一提，C 组（放宽 clip 但只训 150 轮）只到 56% —— **放开步长没用，缺的是时间**。
这反过来确认了瓶颈是"切换需要多少轮"，不是"每步能跨多大"。

**④ 顺带一个口径提醒：** `dist` 冷启动这里报 10%，前面报 2%。
两个数都是真的——2% 是"最后一轮"的成绩，10% 是"训练过程中最佳权重"的成绩。
**报最后一轮还是报最佳，也是评测协议的一部分**，和部署方式一样要说清楚。

**这一节的教训，比 86% 这个数本身更值钱：**

> "调参没用"这个判断，必须先排除"奖励写错了"才能下。
> 奖励是唯一的、既决定信号密度又不改环境动力学的东西 ——
> 它有问题的时候，所有超参搜索都是在错误的地形上找路。

## 实验八：观测噪声 —— 第四个候选，也被推翻了

前三个"让专家失效"的尝试全军覆没（限位反向、延迟反向、死区真失效但 RL 没赢人工 dither）。
观测噪声是第四个候选，而且理由看起来最硬：

> 伺服的控制律 `q_dot = J⁺·(p_target − p_now)` 假设拿到的误差是准的。
> 真实编码器 / 视觉反馈都有噪声，J⁺ 会把噪声一起放大 gain 倍 —— 它一定抖。

设计（`task_noise.py`，约 10 分钟）：给观测的 dx/dy 维加高斯噪声，σ 从 0 扫到 0.2 m
（TOL=0.05 m，所以 σ=0.1 就是"测量误差是够到阈值的两倍"）。
每个 σ 下伺服都**扫 gain 取最优**（不重犯基准错），另外配一个传统工程解
——对误差做滑动平均低通滤波（win=3/5，同样扫参）。
RL 侧冷启动 + `progress` 奖励，**训练环境与评测环境同分布同强度**（σ=0.1）。

| 方案 | 成功率 | 平均步数 |
|---|---|---|
| 伺服 σ=0.00 | 98.0% | 67.2 |
| 伺服 σ=0.02 | 98.0% | 129.1 |
| 伺服 σ=0.05 | 98.0% | 129.5 |
| 伺服 σ=0.10 | 98.0% | 130.6 |
| 伺服 σ=0.20 | 98.0% | 68.7 |
| **伺服 + 低通 win=3（任意 σ）** | **100.0%** | — |
| PPO 冷启动 σ=0.10，贪心部署 | 32.0% | 155.7 |
| PPO 冷启动 σ=0.10，采样部署 | 38.0% | 147.6 |

**伺服一点没掉，低通滤波直接 100%，RL 反而只有 32%。**

三个机制，解释了为什么"噪声让专家失效"这个想当然的假设是错的：

1. **"进入 tol 即停"这个判据本身对噪声免疫。**
   成功不需要稳定住，只要某一瞬间末端落进半径 5 cm 的圈里。
   抖动不减少命中的机会，反而**增加**了穿越边界的概率。
   低通滤波的价值也因此不在成功率（裸伺服已经 98%），而在稳定性和残距 ——
   而这两个指标本实验没有测（见下方设计失误）。
2. **伺服有 gain 这个旋钮，最优值随噪声左移。** 无噪时最优 gain=1.0，
   σ≥0.02 之后最优变成 0.5（低增益不放大噪声，代价是步数从 67 涨到 129）。
   这是教科书级的结论，伺服一个参数就接住了。
3. **RL 输在结构上，不是训练不够。** 同分布噪声、400 轮、`progress` 奖励
   （这个奖励在无噪时能到 86%），仍然只有 32%。
   原因：**无状态策略看不到历史**。低通滤波的本质是时间维度上的信息累积
   （滤波器内部有 deque），而 MLP 策略每一帧都是独立决策，
   它没有办法"多看几帧再平均"。RL 不是没见过噪声，是架构上看不见历史。

### 设计失误，如实记

本节原计划用一个诊断指标量化"在目标附近抖"：统计单回合内**曾进入 tol 的次数**，
想的是"无噪时 1 次，抖了会反复穿越边界"。
但环境是"进入 tol 立即终止"的，这个数**恒等于成功率**，一点额外信息都没有。
中图（`noise_result.png`）因此是冗余的，伺服 0.98 / PPO 0.32 两条线
分别就是它们的成功率。要真测抖动，得把成功判据改成"进入 tol 后再稳定 N 步"。

### 两个没测的边界

- 结论限于**无状态策略 + 单帧观测**。帧堆叠（stack 4 帧）或加一层 LSTM，
  RL 就获得了"看见历史"的能力，上面的结论不能外推。
- 成功判据若改成"稳定 N 步"，噪声很可能真的让伺服失效
  （它永远无法声明成功）—— 这反而是更贴近真实工装的场景，没做。

## 下一步

1. **圆形障碍物**：还没做。注意把障碍位置写进观测，否则 RL 也"看不见"，那是信息缺失不是难度。
2. **死区做得更真**：现在是固定阈值，真实减速器还有迟滞（起转阈值 > 维持阈值）和速度相关的摩擦。
3. **观测噪声补上"稳定 N 步"判据重做**：现在的判据对噪声免疫，
   换成"稳定 N 步"才能测出抖动对宣称成功的真实影响。
4. **帧堆叠 / LSTM 策略**：验证"RL 输在无状态"这个判断 ——
   给它历史观测，它应该能学出自己的滤波。
5. **HER（后见经验回放）/ 课程学习**：现在有了 `progress` 奖励，稀疏性问题已大幅缓解，优先级降低。

## 诚实的边界

四条，都不能含糊：

- **在能写出方程的场合，伺服依然领先**（98% vs 90%），而且差距不会靠调参抹平 ——
  是"知道方程"和"从数据里逼近"的结构性差别。
  RL 的价值不在"打过公式"，在"公式不存在或者不准的时候还能上"，
  以及"用更少的动作做到差不多的效果"（42.1 步 vs 67.2 步）。
- **90% 这个成绩对训练时长很敏感**：同一套配置 150 轮只有 50%，400 轮才是 90%。
  它穿过了一个 U 型谷底。**"我微调了但变差了"不能直接判定方法无效** ——
  得先确认是在谷底，还是真的走错了方向。
- **在模型失配的场合（摩擦死区），RL 补回来了，但没赢过人工 dither**（91.3% vs 95.3%）。
  而且步数多一倍。它能讲的故事是"**不用人先想到要抖**"，不是"比人做得更好"。
- **"让专家失效"这件事，四个候选场景试下来三个是反向的**（限位、延迟、观测噪声都让专家变好或不变），
  只有摩擦死区真的做到了。所以"RL 有用武之地"不能靠想当然，必须一个场景一个场景实证 ——
  这也是本项目最诚实的一条收获。
- **观测噪声下 RL 只有 32%，伺服 98%**。这不是"RL 还没调好"，是**无状态策略看不到历史**的
  结构性限制（低通滤波器有记忆，MLP 没有）。结论不外推到帧堆叠 / RNN 方案（未测）。
- **这个项目不是嵌入式岗的硬通货**。深圳 MCU 岗真正卡的是
  FreeRTOS / DMA / CAN / PID 实物闭环 —— 那些要靠开发板，不靠 Python。
  这个项目对"机器人算法 / 具身智能"方向才是主菜，对嵌入式是加分项。
